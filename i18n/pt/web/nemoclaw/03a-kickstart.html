Módulo 3 · Parte A de 3 · Início de chamadas ao vivo

Conecte a stack do NemoClaw

Nos Módulos 1 e 2, a orquestração ficou no navegador. O workflow terminava quando a página deixava de transportar mensagens, resultados intermediários ou o estado das ramificações. O Módulo 3 transfere os mesmos padrões para um launchable do NemoClaw no Brev. O OpenClaw mantém o histórico da sessão e um workspace em arquivos, além de oferecer ferramentas; o OpenShell limita o alcance do agente em execução. A partir do navegador, você comparará uma API de modelo sem estado com o gateway persistente do OpenClaw.

O diagrama separa três interfaces:

  • REST. Uma solicitação produz uma resposta. Com a Chat Completions API, o cliente inclui o histórico da conversa; uma Responses API pode manter esse estado no servidor.
  • Model Context Protocol (MCP). Um formato de solicitação comum permite que um runtime descubra e chame ferramentas.
  • Gateway do OpenClaw. Um WebSocket em /cli/gateway transporta eventos JSON-RPC da sessão do agente.

Os dois endpoints usados daqui em diante

A rota do modelo não mantém estado e usa uma chave nvapi-. A rota do NemoClaw mantém uma sessão do OpenClaw dentro do OpenShell. Compare a URL, a credencial e o estado de cada uma.

build.nvidia.com

Use a API Chat Completions com uma chave nvapi-. Cada POST inclui as próprias mensagens. Nenhuma ferramenta ou estado de sessão é mantido entre chamadas.

Credencial: chave nvapi-.

Iniciar o NemoClaw no Brev

O OpenClaw roda dentro do OpenShell e mantém a identidade do agente, as ferramentas e a memória da sessão. A configuração abaixo aceita ambas as famílias de hosts Brev compatíveis e se conecta a /cli/gateway.

Credencial: token do gateway. Sessão: x-openclaw-session-key.

As implantações locais usam o mesmo contrato do gateway; siga o playbook de configuração do NemoClaw.

Passo 1 · Teste os endpoints

Os widgets abaixo enviam uma pequena solicitação a cada endpoint e mostram a resposta. Verde significa pronto.

Configurações da rota do modelo

A sonda do modelo é um espelho somente leitura da rota de chat persistente configurada no início do curso ou no Módulo 1a. Altere-a aqui uma vez; o benchmark e as aulas seguintes reutilizam essa rota. As configurações do launchable do NemoClaw abaixo permanecem separadas.

Latência e tempo para o primeiro token entre modelos

Antes de escolher um modelo, meça-o. As células abaixo selecionam modelos do catálogo, enviam o mesmo prompt curto a cada um e registram o tempo até o primeiro token (TTFT) e o tempo total. A célula do catálogo começa aberta para que o filtro fique visível antes da execução do benchmark.

Se a sonda do OpenClaw exceder o tempo limite ou retornar 502. O harness do agente provavelmente ainda está iniciando: o launchable pode ter ficado disponível antes de o OpenClaw carregar a política YAML. Aguarde 30 segundos e execute a sonda novamente. Se continuar indisponível, use a célula Recuperar na seção do gateway.

Solicitação da sonda em código editável

Esta célula expõe a mesma chamada feita pela sonda. Ela reutiliza a URL, o token, o provedor e a sessão de acesso salvos pela sonda. Edite PATH, METHOD e BODY para enviar outras solicitações. O status, os cabeçalhos e o corpo aparecem abaixo.

TRANSPORT controla como a credencial atinge o launchable:

  • "configured" segue a opção de relay salva acima. O Brev entre origens usa o relay da NVIDIA por padrão.
  • "direct" chama a origem do launchable com credentials: "include", usando o cookie correspondente já presente no navegador.

Em um curso hospedado separadamente no Pages, o modo direto depende de um cookie válido do launchable e da política de resposta entre origens; a rota com sessão de acesso explícita usa o relay. Quando o curso é incorporado ao mesmo launchable do NemoClaw que executa o runtime, o modo direto usa a mesma origem e não precisa do relay.

Passo 2 · O gateway

O endpoint do modelo usa a Chat Completions API, na qual um único POST contém tudo que a chamada precisa.

  • A linha de solicitação é uma única POST para a rota de completações.
  • O corpo JSON carrega model e messages.
  • Um cabeçalho Authorization nomeia o chamador.

OpenClaw também implementa essa rota internamente, mas um curso hospedado separadamente a acessa pela camada de acesso do launchable e pelo relay, não como uma solicitação de navegador sem autenticação.

O canal disponível para você usa outro protocolo: um WebSocket em /cli/gateway que transporta JSON-RPC.

A interface de controle no navegador não usa um canal privado. Ela conversa com o agente pelo mesmo WebSocket em /cli/gateway disponível para você; a única credencial necessária é o token do gateway. A sonda descobre esse token, portanto não é preciso colá-lo. Uma chamada GET /api/agent, autorizada por sua sessão do launchable, devolve o token em agent.dashboardUrl. Deixe o campo vazio para que a sonda o preencha.

Esse token carrega o escopo operator.admin, a mesma autoridade que a UI Control detém. Com ele você pode:

  • models.list lista os modelos oferecidos pelo runtime.
  • cron.add agenda um trabalho que será executado sem sua presença.
  • chat.send com uma sessionKey envia uma mensagem diretamente ao ciclo do agente.

Verifique antes de alterar o runtime

Os launchables compatíveis do NemoClaw normalmente mostram tools.toolSearch=false. Uma configuração personalizada ainda pode ativá-lo; por isso, a verificação de integridade lê o valor ativo antes de Recuperar alterar qualquer coisa:

  • Sintoma: você solicita um comando, nenhuma resposta chega, a execução para de avançar e expira.
  • Causa: toolSearch permite que o modelo acesse ferramentas escrevendo código para uma ponte (tool_search_code · “run bridge code”). O modelo fraco pode ficar preso nessa ponte em vez de chamar exec.
  • Recuperação: execute a verificação de integridade. Se toolSearch estiver ativado e a sonda de exec falhar, Recuperar pode desativá-lo com config.patch. A limpeza de sessões e a reinicialização continuam opcionais.

Com o runtime conectado, você pode enviar uma mensagem ao ciclo do agente. Execute as três células abaixo em ordem. A primeira conecta e lista modelos e tarefas cron. A segunda envia um turno de chat, e a última transmite o rastreamento. Leia-o linha por linha:

  • Cada linha ⚙️ é uma chamada de ferramenta com seus argumentos de entrada.
  • Cada linha ✓/✗ é o resultado dessa ferramenta.
  • O gateway não encaminha o raciocínio do modelo; esse rastreamento de entrada e saída é a visão mais detalhada de cada etapa. Quando uma execução para sem resultado, use a célula de logs acima para acompanhar o runtime.

Cada chat verifica a própria integridade. Se registrar ⚠ DEGRADED, volte aqui, execute Recuperar e tente novamente.

Qualquer pessoa que possa ler o ambiente launchable pode ler esse token, e um leitor do token é um operador com tudo acima. Módulo 4 transforma isso de uma conveniência para a questão de segurança central.

Passo 3 · A memória vive na chave da sessão

Cada chat.send recebe uma sessionKey, que determina o que o turno recorda:

  • Mesma chave, duas vezes: o gateway reidrata o histórico do primeiro turno antes da segunda execução, então o agente responde de uma conversa que seu cliente nunca reenvia.
  • Chave diferente: um começo limpo, nada carregado.

A primeira célula registra um fato e o solicita novamente com a mesma chave. O agente usa um turno que o cliente não reenviou, pois o gateway restaurou o histórico mantido no servidor. As outras duas células permitem gerenciar esse estado.

  • Limpar apaga uma sessão em uma chamada; o próximo turno começa sem histórico. Cada célula de chat também contém uma linha sessions.reset comentada para reiniciar no próprio local.
  • Limpar sessões remove as sessões descartáveis acumuladas durante os testes, inclusive as chaves por execução do Passo 2, e mantém apenas a sessão principal.
A chave de sessão é a única identificação da conversa enviada pelo cliente. A partir dela, o gateway recupera no servidor toda a sessão antes de cada chamada; o cliente não precisa reenviar a transcrição. Duas chaves diferentes sempre identificam sessões separadas, mesmo que as conversas tenham conteúdo idêntico.
