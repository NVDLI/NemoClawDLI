Conecta el stack de NemoClaw

En los Módulos 1 y 2, la orquestación permaneció en el navegador. Un flujo de trabajo terminaba cuando la página dejaba de transportar sus mensajes, resultados intermedios o el estado de sus ramas. El Módulo 3 lleva los mismos patrones de agentes a un launchable de NemoClaw en Brev. OpenClaw conserva el historial de la sesión y un workspace respaldado por archivos, sin dejar de ofrecer herramientas; OpenShell limita lo que ese agente en ejecución puede alcanzar. Desde el navegador, compararás la API de modelos sin estado con el gateway persistente de OpenClaw.

El diagrama separa tres interfaces:

  • REST. Una solicitud produce una respuesta. Con la Chat Completions API, el cliente incluye el historial de la conversación; una Responses API puede conservar ese estado en el servidor.
  • Model Context Protocol (MCP). Un formato de solicitud común permite que un runtime descubra e invoque herramientas.
  • Gateway de OpenClaw. Un WebSocket en /cli/gateway transporta eventos JSON-RPC de la sesión del agente.

Los dos endpoints que usarás a partir de ahora

La ruta del modelo no conserva estado y usa una clave nvapi-. La ruta de NemoClaw mantiene una sesión de OpenClaw dentro de OpenShell. Compara la URL, la credencial y el estado de cada una.

build.nvidia.com

Invoca la API de Chat Completions con una clave nvapi-. Cada POST incluye sus propios mensajes. No conserva herramientas ni estado de sesión entre llamadas.

Credencial: clave nvapi-.

Inicia NemoClaw en Brev

OpenClaw se ejecuta dentro de OpenShell y conserva la identidad del agente, sus herramientas y la memoria de sesión. La configuración inferior admite ambas familias de hosts de Brev compatibles y se conecta a /cli/gateway.

Credencial: token del gateway. Sesión: x-openclaw-session-key.

Las implementaciones locales usan el mismo contrato del gateway; sigue el playbook de configuración de NemoClaw.

Paso 1 · Prueba los endpoints

Los widgets siguientes envían una solicitud breve a cada endpoint y muestran la respuesta. Verde significa que está listo.

Configuración de la ruta del modelo

La sonda del modelo es un reflejo de solo lectura de la ruta de chat persistente configurada al inicio del curso o en el Módulo 1a. Cámbiala aquí una vez; el benchmark y las lecciones posteriores reutilizan esa ruta. La configuración del launchable de NemoClaw que aparece abajo permanece separada.

Latencia y tiempo hasta el primer token por modelo

Antes de elegir un modelo, mide su comportamiento. Las celdas siguientes obtienen del catálogo los modelos coincidentes, transmiten el mismo prompt breve a cada uno y registran el tiempo hasta el primer token (TTFT, del inglés Time to First Token) y el tiempo total de cada modelo. La celda que consulta el catálogo comienza abierta para mostrar el filtro antes de ejecutar el benchmark.

Si la sonda de OpenClaw agota el tiempo de espera o devuelve 502. Es probable que el runtime del agente aún esté arrancando: el launchable puede haberse iniciado antes de que OpenClaw terminara de cargar su política YAML. Espera 30 segundos y vuelve a ejecutar la sonda. Si sigue sin responder, usa la celda Recuperar en la sección del gateway antes de continuar.

La solicitud de la sonda como código editable

El código expuesto realiza la misma solicitud que la sonda. Reutiliza la URL, el token, el proveedor de acceso y la sesión que guardó la sonda. Edita PATH, METHOD y BODY para enviar otras solicitudes. El estado, los encabezados y el cuerpo aparecen debajo.

TRANSPORT controla cómo llegan las credenciales al launchable:

  • "configured" sigue la opción de gateway guardada arriba. Brev entre orígenes usa el relay de NVIDIA de forma predeterminada.
  • "direct" llama al origen del launchable con credentials: "include" y utiliza la cookie correspondiente que ya posee el navegador.

Los launchables con Pomerium conservan su sesión firmada en el navegador. El curso usa sus WebSockets directos y lee los dos endpoints de inicialización mediante una solicitud fija al loopback desde esa terminal autenticada. Los launchables con Cloudflare Access usan el relay alojado y su campo de sesión explícito. Cuando el curso se incorpora al mismo launchable de NemoClaw que ejecuta el runtime, el modo direct utiliza el mismo origen y no necesita el relay.

Paso 2 · El gateway

El endpoint del modelo utiliza Chat Completions API, donde un solo POST contiene todo lo que la llamada necesita.

  • La línea de solicitud es un único POST a la ruta de completions.
  • El cuerpo JSON transporta model y messages.
  • Un encabezado Authorization identifica al emisor.

OpenClaw también implementa esa ruta internamente, pero un curso alojado por separado la alcanza mediante la capa de acceso del launchable y el relay, no como una solicitud de navegador sin autenticación.

El canal que sí está disponible utiliza otro protocolo: un WebSocket en /cli/gateway que habla JSON-RPC.

La interfaz de control de la pestaña del navegador no utiliza un canal privado especial. Se comunica con el agente mediante el mismo WebSocket en /cli/gateway que puedes usar, y la única credencial necesaria es el token del gateway. La sonda descubre ese token para que no tengas que pegarlo. Una solicitud GET /api/agent, autorizada por tu sesión del launchable, lo devuelve en agent.dashboardUrl. Deja el campo vacío para que la sonda lo complete.

Ese token tiene asignado el alcance operator.admin, la misma autoridad que la interfaz de control. Con él puedes hacer lo siguiente:

  • models.list enumera todos los modelos que ofrece el runtime.
  • cron.add programa trabajo que se ejecuta sin tu intervención.
  • chat.send con una sessionKey envía un mensaje directamente al bucle del agente en ejecución.

Comprueba antes de cambiar el runtime

Los launchables compatibles de NemoClaw suelen mostrar tools.toolSearch=false. Una configuración personalizada aún puede activarlo, por lo que la comprobación de estado lee el valor activo antes de que Recuperar cambie algo:

  • Síntoma: pides un comando, no llega ninguna respuesta, la ejecución se detiene y termina por agotar el tiempo de espera.
  • Causa: toolSearch permite que el modelo acceda a herramientas escribiendo código para un puente (tool_search_code · “run bridge code”). El modelo débil puede quedar atrapado en ese puente en lugar de llamar exec.
  • Recuperación: ejecuta la comprobación de estado. Si toolSearch está activado y falla la sonda de exec, Recuperar puede desactivarlo con config.patch. La limpieza de sesiones y el reinicio siguen siendo opcionales.

Una vez preparado el runtime, puedes enviar un mensaje al bucle del agente. Ejecuta los tres nodos siguientes en orden: el primero conecta con el gateway; el segundo enumera modelos y tareas cron; el tercero envía un turno de chat y transmite la traza. Lee la traza fila por fila:

  • Cada fila ⚙️ es una llamada a herramienta con sus argumentos de entrada.
  • Cada fila ✓/✗ es el resultado de esa herramienta.
  • El razonamiento del modelo no se envía por el gateway, por lo que esta traza de entrada y salida ofrece la vista por pasos más detallada. Cuando una ejecución se detenga sin resultado, usa la celda de logs anterior para monitorizar el runtime.

Cada ejecución de chat comprueba su estado. Si aparece ⚠ DEGRADED, vuelve aquí, ejecuta Recuperar y repite el intento.

Cualquiera que pueda leer el entorno del launchable también puede leer ese token; quien posea el token es un operador con todas las capacidades anteriores. El Módulo 4 convierte esta comodidad en la pregunta central de seguridad.

Paso 3 · La memoria vive en la clave de la sesión

Cada chat.send recibe una sessionKey, que determina lo que el turno recuerda:

  • La misma clave, dos veces: el gateway restaura el historial del primer turno antes de ejecutar el segundo, por lo que el agente responde a partir de una conversación que el cliente nunca volvió a enviar.
  • Una clave distinta: comienza desde cero, sin conservar nada.

La primera celda introduce un dato y después pide recuperarlo con la misma clave. El agente responde a partir de un turno que tu cliente nunca reenvió, porque el gateway reconstruyó ese historial en el servidor. Las otras dos celdas te permiten gestionar el estado almacenado:

  • Limpiar borra una sesión con una sola llamada; el turno siguiente comienza sin historial. Cada celda de chat también contiene una línea sessions.reset comentada para reiniciar allí mismo.
  • Limpiar sesiones elimina las sesiones desechables acumuladas durante las pruebas, incluidas las claves por ejecución del Paso 2, y conserva únicamente la sesión principal.
La clave de sesión es la única identificación de la conversación enviada por el cliente. A partir de ella, el gateway recupera en el servidor toda la sesión antes de cada llamada; el cliente no necesita reenviar la transcripción. Dos claves diferentes siempre identifican sesiones separadas, aunque las conversaciones tengan contenido idéntico.
